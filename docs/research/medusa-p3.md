> 2026-10-13 由 6 個研究代理對照**已安裝的 2.21.2 原始碼**（`node_modules/.pnpm/@medusajs+*@2.21.2_*`）與官方文件（docs.medusajs.com）查證。原始碼與文件不一致時以原始碼為準。`verified-in-source`＝已在原始碼確認；`docs-only`＝僅文件；`inferred`＝推論，不可當事實。

## 本專案據此做的決定

1. 示範種子 `initial-data-seed.ts`（建歐洲區與 T-shirt）已刪除，改為 `drn-0001`～`drn-0004` 四支可重跑的 migration script。**已上線過的 script 檔名永不改名**（以檔名追蹤，改名會在既有資料庫再跑一次）。
2. 含稅價由**商店幣別**的 price preference（`supported_currencies[].is_tax_inclusive`）決定；Region 的設定只影響帶 region 規則的價格，兩者都設為 true。
3. 金額以主幣單位儲存（1150＝NT$1,150）。Medusa 不做進位：含稅價拆稅後的小計／稅額會有小數，**總額**只在單價、運費、折扣都是整數時才是整數。→ ECPay provider 收到非整數金額一律拒絕（fail closed）；百分比折扣需另做整數化（P5-05）；電子發票稅額依台灣規則另算（P4-06）。
4. **部署時 migration 拆兩步**：`medusa db:migrate --skip-scripts` 然後 `medusa db:migrate:scripts`。因為 2.21.2 的 `db:migrate` 在 script 失敗時仍回傳 0；單獨跑 scripts 的離場碼才可信。正式環境一律從編譯後的 `.medusa/server` 執行（記錄的檔名為 `.js`），同一個資料庫不可混用 `.ts`／`.js`。
5. RBAC：需同時設 `featureFlags.rbac` **與**在 modules 明列 `@medusajs/medusa/rbac`（defineConfig 在 flag 註冊前就決定是否載入模組）。政策鍵為 `resource:operation`。沒有角色的使用者在有政策的路由一律 403；角色變更要重新登入才生效。
6. 整合測試：test-utils 只讀 `DB_HOST/DB_PORT/DB_USERNAME/DB_PASSWORD`（不讀 DATABASE_URL），`DB_HOST` 必須含 `localhost`；migration scripts 不會在測試中執行，測試自行呼叫 `drn-*` 函式。
7. `medusa exec <file> [args..]` 只傳位置參數（`--flag` 會被 yargs 吃掉）。

## TWD currency handling in Medusa 2.21.2 (major units, TWD currency metadata, tax-inclusive rounding, ECPay integer TotalAmount)

(a) Yes. Medusa v2 stores and returns money in major units, so 1150 means NT$1,150. All amounts are BigNumber values that are kept to 20 significant digits (raw_* {value, precision:20}), and the totals code never rounds them to the currency's minor unit. (b) The installed @medusajs/utils defaultCurrencies entry for TWD is { symbol: "NT$", symbol_native: "NT$", name: "New Taiwan Dollar", decimal_digits: 2, rounding: 0, code: "TWD" }. Note decimal_digits is 2, not 0. The currency module loader upserts these defaults into the currency table on every boot, so editing decimal_digits in the DB will not stick. The totals and payment code read utils' defaultCurrencies (or Intl.NumberFormat, which also gives 2 for TWD) rather than the DB row anyway. (c) Medusa never rounds totals. With tax-inclusive prices (price preference is_tax_inclusive), subtotal and tax_total come out fractional (1150/1.05 = 1095.238…). total stays an integer only when every unit_price, shipping amount and adjustment is an integer. A percentage promotion (10% of 333 = 33.3) or tax-exclusive pricing (total 4022.85 in my run) gives a fractional cart.total. The payment collection amount is cart.raw_total unrounded, so it reaches the payment provider's initiatePayment unrounded. Integer totals have to be enforced by the project: (1) set a tax-inclusive price preference for TWD/region, (2) use only integer prices, shipping and fixed promotions, or guard percentage promotions, (3) check in the ECPay provider that the amount is an integer before sending TotalAmount. The guard should fail closed, or round half-up and record the difference. The docs agree with the installed source on major units. The docs found say nothing about TWD decimal_digits or rounding, so on those points the source is the authority.

## Semantics of src/migration-scripts in Medusa 2.21.2 (run-once data migrations) vs `medusa exec`, plus a production-safe Taiwan seed design

From the installed 2.21.2 source:

(a) When they run and how they're tracked. Migration scripts run as the last phase of `medusa db:migrate` and `db:setup`. That phase runs in a forked `db:migrate:scripts` child process, and `--skip-scripts` turns it off. You can also run the phase alone with `medusa db:migrate:scripts`. `medusa start` and `medusa develop` never run them. Each script runs once per database. Runs are tracked in the table `script_migrations`, which has the columns id SERIAL, script_name VARCHAR(255) with a UNIQUE index, created_at and finished_at. The key is `path.basename(file)`, so it includes the extension: a dev run records "initial-data-seed.ts", while the compiled build in .medusa/server would record "initial-data-seed.js". A script counts as done only when finished_at is set. Order: Medusa's own core scripts run first, then plugin scripts, then the app's `<cwd>/src/migration-scripts/*.{ts,js}`. Within each folder, files run in `localeCompare` order of their file names.

(b) Transactions and failure. There is no database transaction around a script. The script just receives `{ container }`, and each workflow it calls commits on its own or rolls itself back through compensation. If a script throws, it has already inserted a row with finished_at NULL, and that row stays. The error is logged and the db:migrate:scripts child exits with code 1, so later scripts in that run do not run. The failed script then runs again from the top on every later db:migrate, with the warning "did not complete during a previous run". A partly finished, non-idempotent script will therefore create duplicates on the retry.

**Critical gotcha:** in 2.21.2, `db:migrate` ignores the exit code of the scripts child process. It still returns true and exits 0 when a migration script fails (migrate.js:115-122), so CI or deploy cannot detect the failure from that exit code. Concurrency is guarded by a LOCKING-module lock plus a per-script `pg_try_advisory_lock`.

(c) `medusa exec` is different. It runs any file, every time you call it, with no tracking, and passes `{ container, args }`. It boots the full app loader, which also runs `createDefaultsWorkflow`: that creates a default store with EUR, a "Default Sales Channel" and a publishable key if none exist. Migration scripts use only `MedusaAppLoader` plus workflow hooks. They do not load subscribers or jobs, and they do not run `createDefaultsWorkflow`.

(d) Deleting or renaming initial-data-seed.ts after it already ran on the dev DB:
- **Deleting it** has no effect on the existing DB. The row and the seeded data stay, and nothing is undone. A fresh or production DB will simply never run it.
- **Renaming it**, or adding any new file name, makes it pending, and it runs on the existing DB at the next db:migrate. The template seed has no existence checks, so a renamed copy would create a second sales channel, API key and store, then most likely fail on regions whose countries are already assigned. That failure would be retried on every migrate.
- The same applies to any new script name: it will run on existing DBs, and that is the intended way to ship a new data change.

(e) Best practice:
- Production data such as the store, region, tax region, stock location and catalog goes in a migration script with a new, sortable name. Each step should check whether the data already exists (look it up by handle, name or country) and create only what is missing, so a retry after a partial failure is harmless.
- Do not end the script early because of the environment: an early return still marks the script finished, permanently. If a script must be conditional, use `defineFileConfig({ isDisabled })`. Disabled files are skipped before they are claimed, so they get no row and stay pending.
- Dev-only data such as stock quantities goes in an idempotent `medusa exec` script that refuses to run when NODE_ENV=production.

**Recommendation for this project:**
1. Neutralize the template's EU demo `initial-data-seed.ts` before any production DB exists. Delete it or replace it, but do not rename it.
2. Add `src/migration-scripts/drn-0001-tw-store-and-catalog.ts`. It upserts the TWD store, the Taiwan region, the tw tax region, the TW warehouse with its sales-channel link, and the 3 products, with inventory levels at stocked_quantity 0.
3. Add `src/scripts/dev-add-test-stock.ts`, run with `medusa exec`. It sets test stock through `batchInventoryItemLevelsWorkflow` and refuses to run in production.
4. In deploys, run `medusa db:migrate --skip-scripts`, then run `medusa db:migrate:scripts` as a separate step. That step's exit code does reflect script failures.

## Taiwan region with tax-inclusive TWD pricing and a 5% default tax rate, created in a Medusa 2.21.2 migration script

I checked everything against the installed 2.21.2 source under node_modules/.pnpm, and the docs agree with it.

(a) createRegionsWorkflow takes { regions: (CreateRegionDTO & { payment_providers?, is_tax_inclusive? })[] }. CreateRegionDTO has name, currency_code, automatic_taxes?, countries?, payment_providers? and metadata?. automatic_taxes defaults to true in the model. The workflow removes is_tax_inclusive and payment_providers from the region record. It then always creates a price preference {attribute:'region_id', value:<new id>, is_tax_inclusive} through createPricePreferencesWorkflow.runAsStep. If is_tax_inclusive is left out, that preference is stored as false.

(b) Tax-inclusive pricing is not a column on the region. It lives only in PricePreference rows (attribute region_id or currency_code), and (attribute, value) must be unique. When prices are calculated, the region preference wins only if the chosen price has its own region_id rule equal to the context region. Otherwise the currency_code preference applies, and with neither the default is false. Most product prices are plain TWD prices with no region rule, so the deciding switch is the TWD currency preference. You set it through the store's supported_currencies[].is_tax_inclusive. The cart copies is_calculated_price_tax_inclusive onto line_item.is_tax_inclusive. Totals then back the tax out of the price: subtotal = unit_price*qty/(1+rate/100), and the total stays at the shelf price.

(c) createTaxRegionsWorkflow takes a plain array CreateTaxRegionDTO[], not wrapped in an object. Each entry has country_code, province_code?, parent_id?, provider_id?, metadata?, created_by?, and default_tax_rate?: { rate?, code?, name, metadata? }. rate is a percentage (5 means 5%). code is optional in the TS type but NOT NULL in the TaxRate model, so always pass it. 'tp_system' is registered automatically as 'tp_'+identifier ('system').

The docs from context7 agree with the installed source on every point I compared, so nothing needed overriding.

Workflow inputs:
- createSalesChannelsWorkflow takes { salesChannelsData: CreateSalesChannelDTO[] }, where each item is { name, description?, is_disabled? }.
- createApiKeysWorkflow takes { api_keys: { title, type: "publishable" | "secret", created_by }[] }.
- linkSalesChannelsToApiKeyWorkflow and linkSalesChannelsToStockLocationWorkflow both take LinkWorkflowInput, which is { id, add?: string[], remove?: string[] }. For the first, id is the api key id; for the second, id is the stock location id.
- createProductsWorkflow takes products[i].sales_channels?: { id: string }[]. For products that already exist, use linkProductsToSalesChannelWorkflow { id: sc_id, add: [prod_ids] }. Do not use updateProductsWorkflow with sales_channels for this: it dismisses all existing channel links on the product and replaces them.
- The store default is set with updateStoresWorkflow { selector: { id }, update: { default_sales_channel_id } }.

How the Store API scopes by key: the framework mounts ensurePublishableApiKeyMiddleware on every /store route. It reads the `x-publishable-api-key` header and looks up the api_key by `token` and type=publishable. It rejects missing or revoked keys. It then sets req.publishable_key_context.sales_channel_ids from the key's linked channels. On GET /store/products, filterByValidSalesChannels does three things:
- It sets the sales_channel_id filter to the key's channels.
- It throws if the key has no channels.
- It throws if a `sales_channel_id` query parameter names a channel outside the key.

The product_sales_channel link filter is then applied, together with a status=published default. Watch out: on the list route, if the database has only one sales channel in total, the channel filter is dropped. For carts, a key linked to exactly one channel gets that channel assigned automatically. A key linked to two or more channels means the request body must include sales_channel_id. So keep each storefront's key linked to its own single channel.

Reading the key: the database column and DTO field are both named `token`. Publishable tokens are stored in plain text ("pk_" + 64 hex characters, salt ""). Secret keys are stored hashed, and the service blanks their token on reads. So `query.graph({ entity: "api_key", fields: ["id","token","title","revoked_at","sales_channels.id"], filters: { type: "publishable", title } })` returns the usable token for tests (the `x-publishable-api-key` header) and for the storefront env.

On every boot, createDefaultsWorkflow guarantees a sales channel ("Default Sales Channel"), a store whose default is that channel, and, only if no publishable key exists at all, a "Default Publishable API Key" linked to it. The script below therefore creates the two named channels next to the default one. That gives 3 or more channels, so the list filter is active. It then repoints the store default to Official Store.

Link creation uses upsertMany, so re-running an add is safe. The script is idempotent: it skips a channel that already exists with the same name and a key that already exists with the same title.

## Medusa 2.21.2 admin RBAC: feature flag, roles/policies creation, policy keys, user assignment, no-role behavior, enforcement

I checked everything below against the installed 2.21.2 source, which overrides the docs where they disagree.

(a) RBAC is off by default. It sits behind the feature flag `rbac` (env var `MEDUSA_FF_RBAC`, default false). There is a second, separate flag `rbac_filter_fields` (`MEDUSA_FF_RBAC_FILTER_FIELDS`). The flag can be set with `featureFlags: { rbac: true }` in medusa-config or with `MEDUSA_FF_RBAC=true`; the env var wins if both are set. There is a load-order catch. `defineConfig()` decides whether to load the RBAC module (`disable: !FeatureFlag.isFeatureEnabled("rbac")`) while medusa-config is being read. At that point the core `rbac` flag is not registered yet, because core flags load after `configLoader`. I reproduced this in isolation: with `featureFlags: { rbac: true }` plus `MEDUSA_FF_RBAC=true`, the result was `{"resolve":"@medusajs/medusa/rbac","disable":true}`. To be safe, also add `{ resolve: "@medusajs/medusa/rbac" }` to the `modules` array. A later entry with the same name replaces the default one, and the result has no `disable` flag. Then run `db:migrate`.

(b) Use `createRbacRolesWorkflow` from `@medusajs/medusa/core-flows`. Its input is `{ actor_id?, actor?, roles: [{ name, description?, metadata?, parent_ids?, policy_ids? }] }`. `policy_ids` are policy IDs, not keys. The permission check (`validateUserPermissionsStep`) only runs when `actor_id` is passed. Other workflows: `createRbacPoliciesWorkflow` (`{ policies: any[] }`), `createRbacRolePoliciesWorkflow` (`{ actor_id?, actor?, policies: [{ role_id, policy_id }] }`), and the matching update/delete workflows. The module service (`Modules.RBAC`) also has `createRbacRoles`, `createRbacRolePolicies`, `listRbacPolicies({ key })` and similar methods.

(c) Policy key = `${resource}:${operation}`, joined with a colon. So it is `product:read`, not `product.read`; the docs' `product.read` is just a free-form key in an SDK example. Built-in policies are generated as resource × {read, create, update, delete}, and they are saved to the database when the app starts. On every start the module also soft-deletes any policy that is not defined in code. So custom policies must be defined in code with `definePolicies` in `src/policies`. Policies created only through the API or workflow will disappear at the next restart. The built-in Super Admin uses key `*:*` (`rpol_super_admin`, role `role_super_admin`), and wildcards are honoured.

(d) Users are linked to roles through a link table, `user_rbac_role`. Ways to assign:
- `createUsersWorkflow` with `users[].roles: string[]`
- invites with `roles`
- `assignUserRolesWorkflow({ actor_id, actor?, user_id|user_ids, role_id|role_ids })`. This checks that the actor already has every policy in the roles being assigned.
- the admin endpoint POST `/admin/rbac/roles/:id/users`
- directly with `link.create({ [Modules.USER]: { user_id }, [Modules.RBAC]: { rbac_role_id } })`, which is what Medusa's own migration script does

Role IDs are copied into the login token (`app_metadata.roles`) when the user logs in. A user must log in again before a role change takes effect.

(e) A user with no role is denied on every admin route that declares policies; the request fails before any policy is looked up. Routes without policies, such as `/admin/users/me`, still work. Existing users are covered by a one-time migration script, `create-super-admin-role`, which runs when RBAC is enabled and gives every existing user the Super Admin role. Any user created later needs a role assigned explicitly.

(f) When RBAC is on, the API loader adds a permission check to every route or middleware that declares `policies: [{ resource, operation }]`. A denied request gets HTTP 403: `Forbidden` when the user has no roles, or `Insufficient permissions. Required policies: <resource>:<operation>, ...` when the roles don't cover the route.
