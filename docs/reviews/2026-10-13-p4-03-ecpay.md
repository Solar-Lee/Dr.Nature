# P4-03 綠界金流審查紀錄（2026-10-13）

4 個視角（付款安全、Medusa 正確性、綠界規格、測試可信度），每條發現由 2 名懷疑者嘗試推翻；共 24 個代理。

| 票數 | 嚴重度 | ID | 摘要 | 處置 |
|---|---|---|---|---|
| 2/2 | high | ecpay-test-1 | No test covers creating a new payment session after the order exists (the planned 'pay again from the order page' flow). When that happens, ECPay's signed 'paid' notice for the old trade gets '0\|Session mismatch' on every retry, so the shopper is charged but the order never shows as paid. | 修正：訂單成立後禁止建立新付款 session（middleware）；重新付款待 P4-09 設計。新增測試。 |
| 2/2 | medium | ECPAY-1 | A signed, paid ReturnURL notice is only accepted if an immediate QueryTradeInfo call already reports TradeStatus=1. ECPay's own docs say a credit-card trade can still read 0 right after payment, and the call depends on a response format nobody has verified. The signed notice's RtnCode=1 is never used as the basis for marking the order paid. | 修正：已驗章且綁定 session 的通知本身即為付款證明；authorizePayment 不再連線綠界（結帳與回呼路徑零 QueryTradeInfo）。QueryTradeInfo 只留給 getPaymentStatus／P4-10 對帳。測試斷言 stubRequests=0。 |
| 2/2 | medium | ecpay-deleted-session-paid-notice-rejected | Medusa can delete a pending ECPay session while its signed checkout form can still be paid. If the shopper then pays that form, the ReturnURL route answers 400 every time ECPay sends the notice, and the payment is never recorded. | 修正：主要成因由上述 middleware 消除；結帳前替換 session 的情境改為帶 [ECPAY-ALERT] 的 400（綠界持續重送＝持續告警），SOP 見 docs/ops/ecpay-manual-refund.md。新增測試。 |
| 2/2 | medium | ecpay-capture-on-canceled-order | A paid ReturnURL notice for an order that was canceled while unpaid still captures the payment, flips the canceled collection back to completed and returns '1\|OK'. Nobody is alerted. | 修正：已取消訂單不入帳，改記錄在訂單 metadata（ecpay_paid_after_cancel）並告警、回 1|OK。新增測試。 |
| 2/2 | medium | ecpay-test-3 | The refund test only checks that the provider throws. It never runs an admin refund or an order cancel on an order paid through ECPay, so it misses that a paid order can then be neither cancelled nor marked refunded in Medusa. | 修正：已付款訂單可取消／退款；退款記為 manual_pending 並告警，由 Super Admin 於綠界後台執行（SOP）。新增測試。 |
| 2/2 | low | ecpay-orphaned-paid-trade | When a payment session is replaced, its ECPay trade still accepts payment. A paid notice for that trade is then rejected with 400 forever, so ECPay takes the shopper's money and Medusa never records it. | 同上。 |
| 2/2 | low | ecpay-test-4 | No test covers a paid notice that arrives before the cart is completed: processPaymentWorkflow then captures the payment and tries completeCartAfterPaymentStep, and the route's 'cart has no order' branch never runs. | 修正：新增「付款通知早於購物車完成」測試（建立訂單並入帳）。 |
| 2/2 | low | ecpay-test-5 | No test checks OrderResultURL or ClientBackURL in the signed form (in the unit or the integration spec), and config.ts (ecpayOptionsFromEnv, including the guard against ECPAY_API_BASE_URL in prod) has no tests at all. | 修正：表單測試斷言 OrderResultURL／ClientBackURL；新增 config.unit.spec.ts（含正式環境禁止 ECPAY_API_BASE_URL）。 |
| 1/2 | medium | ecpay-test-2 | The QueryTradeInfo stub always answers at once with the final status and never rate-limits. The happy-path test sets the trade to paid before posting the notice, so it hides that the route sends '1\|OK' only after QueryTradeInfo already reports paid. Real ECPay documents a delay before a paid trade shows up and blocks callers who query too fast. | 隨 ECPAY-1 一併消除（回呼不再依賴 QueryTradeInfo）。 |
